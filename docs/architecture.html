01 / OVERVIEW

消息优先，而不是命令平台

MVP 的核心只有 conversation、participant、message、agent_delivery 与 workspace_binding。一次 Agent 执行的 run、流式 event、通用 job 与 workflow 均不是首版持久化核心。

Accepted

产品边界

用户发消息，云端提交；目标 workspace 的本地 Agent 执行；结果再成为一条普通聊天消息。

Accepted

传输语义

at-least-once + stable ID + 幂等去重。ACK 表示本地已耐久接管，不表示 Agent 已完成。

Proposed

本地增强

每 workspace 使用独立 SQLite inbox/outbox，双向消息都能跨断线与子进程重启恢复。

可靠性目标：WebSocket 所属进程重启时连接一定会断；我们保证的是 committed message 不丢、自动重连、按序 replay 与重复抑制，而不是声称 TCP 连接永不断。

02 / TOPOLOGY

两个本地应用，N 个 workspace 子进程

coforge-computer 与 coforge-daemon 是两个独立 OS 进程，通过 Unix socket typed RPC 通信。workspace-daemon 是后者包内的运行时角色，不是第三个 app/package。

本地职责

  • computer：安装、更新、daemon 生命周期；
  • daemon：期望/实际 workspace 集合、崩溃退避；
  • workspace child：WSS、顺序、去重、spool、ACP。

云端职责

  • Caddy：TLS、健康路由与连接 drain；
  • gateway：只拥有 live socket，不访问业务数据库；
  • backend + PostgreSQL：业务事务与恢复真相。
03 / DELIVERY

双向耐久，而不是只补 server → daemon

参考 Multica 的 delivery / ACK 原则，但不 1:1 复制。CoForge 还要保证 Agent 响应从离线设备回云端时可重试，因此本地 inbox 与 outbox 必须对称。

01提交消息

同一数据库事务写 canonical message 与每目标 Agent 的 delivery。

02唤醒 Gateway

通知只是 hint；丢失后由 backend reconciliation 与 cursor replay 修复。

03投递 Offer

通过 workspace child 自己的 WSS session 发送稳定 delivery_id。

04本地接管

SQLite inbox 插入成功并去重后才回 accepted ACK。

05ACP 执行

Agent 最终响应先进入本地 durable outbox。

06幂等回传

用 client_message_id 重试，服务端只生成一条 canonical response。

稳定身份

message_id 是 canonical message；delivery_id 是一次 message → Agent 投递；client_message_id 是消息发送侧幂等键；连接与 retry attempt 仅供诊断。

顺序与背压

数据库事务分配 conversation_seq。同一 Agent context 按序处理；不同 Agent 可并发。连接队列满时背压或断开，不能静默丢弃 durable delivery。

04 / RECOVERY

把重启变成可恢复事件

两副本与 rolling drain 降低中断概率；durable state、重连与幂等才真正防止数据丢失。

故障即时影响恢复机制不变量
Gateway 重启该实例 WSS 断开Caddy 将重连路由至健康副本；按 cursor replay未 ACK delivery 仍在 PostgreSQL
workspace child 崩溃ACP 与 WSS 暂停daemon 退避重启；读取本地 SQLite inbox/outbox已接管消息不会因进程死亡丢失
ACK 丢失云端认为尚未接管重发同一 delivery_id；本地唯一键去重ACP 不重复消费已完成投递
响应回传中断服务端未确认提交本地 outbox 重发同一 client_message_id只形成一条 canonical response
Wakeup 丢失在线推送延后backend reconciliation 与 reconnect replay通知不是 durable source
慢连接连接内队列上升有界队列、背压、超限断开并 replay不在内存队列静默丢消息
05 / PROTOCOL

版本化 typed RPC over WSS

方法名使用 CoForge 自己的 vocabulary。每个 envelope 携带 protocol_version、request_id、workspace/session scope，并用 major version 拒绝不兼容连接。

session.*hello · ready · resume
delivery.*offer · accepted · rejected
message.*publish · committed
heartbeat.*ping · pong

“daemon 不用 HTTP”仅约束 daemon ↔ cloud 的传输。浏览器 bootstrap、认证与普通 Web 读取仍可使用 HTTPS；browser API 与 cloud internal RPC 是独立契约。

06 / DECISIONS

已定边界与下一批 ADR

架构文档定义方向；会锁定 wire format、存储 schema 或迁移成本的细节必须单独写 ADR。

Accepted

当前约束

  • 无 Next.js；Web/backend 使用 TanStack + Node 24；
  • 本地 TS 使用 Bun 1.4，Gateway 使用 Go；
  • 本地仅 computer / daemon 两个发布应用；
  • Docker + Caddy + 两副本 + managed PostgreSQL；
  • MVP 采用轻量 CR：短生命周期 feature branch、一位 Agent review、短检查后立即 squash/rebase，禁止直接 push main；
  • 只有架构、schema、协议、许可证、安全边界等高影响事项需要 Frank 明确批准；
  • 版本由 mise 统一管理。
Proposed

待 ADR 锁定

  1. WSS encoding 与 schema generation；
  2. gateway ↔ backend 内部传输；
  3. SQLite schema、加密、保留与修复；
  4. conversation_seq 高并发分配；
  5. ACP capabilities 与 cancellation；
  6. reconnect / drain 的量化 SLO；
  7. 设备身份、密钥轮换与 workspace revoke。

首批故障测试

  1. 重复 offer 在本地接管后最多进入 ACP 一次
  2. child 接管后崩溃能从 inbox 继续
  3. 离线 Agent 响应重连后只提交一次
  4. publish 中 gateway 死亡不产生双写
  5. 单副本滚动时另一副本接受重连
  6. 丢失 wakeup 可由 scan / replay 修复
  7. 跨重连保持 conversation 顺序
  8. workspace revoke 后停止 replay 与执行

Reference, not template. Multica 的 delivery contract 与 runtime ownership ADR 用来验证故障模式，不作为 1:1 实现模板。CoForge 增加了双向本地 outbox、幂等 Agent-response publish、版本协商与自己的协议 vocabulary。
