# CoForge 产品界面设计指导

适用范围：CoForge Web 工作台、对话、列表、设置和相关产品交互。这里约束设计判断，不规定所有页面套用同一种布局，也不要求借本次任务重做无关页面。

## 1. 来源与优先级

- 保留真实业务含义、用户任务、权限与安全要求，以及可访问性；不能为了简洁隐藏风险或改变事实。
- 颜色以 Figma 与 [design-tokens.md](design-tokens.md) 的维护约定为准；实现复用 [styles.css](../apps/web/src/styles.css) 和 [UI primitives](../apps/web/src/components/ui)。本文不重复维护 Token 值。
- 复用宿主的 TanStack Start、Tailwind、Base UI、图标和本地化约定。不引入另一套主题、组件库或 Vercel 品牌 CSS。
- 本文负责内容层级、渐进披露和评审方法。Figma 尚未确定的字体、间距等不得由 Agent 编造成已批准的品牌标准；当前实现也不自动等于认可的设计范例。
- `design-taste-frontend` 的营销页规则不作为工作台默认值。不要为“去 AI 味”删除现有品牌紫、真实状态点、有效列表或表格，也不要强制添加图片、非对称布局或动效。

## 2. 先确定用户任务，再选布局

开始设计前，用一句话说明谁在这里完成什么任务，并明确主内容、主要操作、需要时才查看的细节。检查现有页面与相关设计稿，保留已经有效的交互。

- 对话页突出交流对象、消息和回复入口，不在它们之前放欢迎 Hero、口号或无关统计卡片。
- 设置页突出可修改的选项、当前值和保存结果，不写一段介绍页面用途的开场白。
- 比较任务让可比较的项共享列、基线和单位；精确查找用表格，关系确实更容易看懂时才用图表。
- 如果有多个合理布局，先比较两个信息结构不同的方案，选择最少阅读和操作成本的那个。不要只换配色来制造不同方案。
- 第一屏应让用户辨认当前上下文与下一步。主次通过分组、位置、字号角色和留白建立，不靠给每块内容加卡片。

统一视觉语言，不统一所有页面的轮廓。真正同级的条目应保持一致；内容的重要性不同，不能为了对称给它们同等视觉权重。

### 2.1 列表与详情使用一致的导航逻辑

以下规则来自已确认的消息页交互，作为新增或修改同类页面的默认约定，适用于“从列表选择一个对象，再查看或操作详情”的页面，例如会话列表与聊天、电脑列表与电脑详情。独立表单、设置分组等没有列表—详情关系的页面不强行套用；确需不同交互时，先说明用户任务与差异原因，再确认例外。本文是交互规则的维护位置，`AGENTS.md` 只保留执行要求和模块归属。

先区分三个层级：全局导航负责 Workspace、成员、消息、电脑和个人设置入口；对象列表负责选择会话或电脑；详情负责当前对象的内容和操作。不要把全局导航与会话历史列表当成同一个侧栏。

| 场景                 | 默认操作逻辑                                                                                                   |
| -------------------- | -------------------------------------------------------------------------------------------------------------- |
| 桌面有足够宽度       | 可同时显示全局侧边栏、对象列表和详情；保留已有选中态和侧边栏折叠能力。                                         |
| 手机打开列表入口     | 先显示列表；顶部是一行“菜单入口＋页面名称＋必要的页面操作”，不要自动跳过列表进入首个对象。                     |
| 手机选择对象         | 用详情替换列表所占的主内容区域；顶部是一行“返回列表＋对象名称＋必要的对象操作”，不把列表和详情压缩后继续并排。 |
| 手机直接打开详情链接 | 打开该对象的详情，不强制先选一次；仍提供明确的返回列表入口。                                                   |
| 从详情返回列表       | 回到同一列表上下文，保留滚动位置以及已有的筛选、搜索和选中状态；仅切换面板不得清空未提交的草稿。               |

- **菜单与返回不可混用**：菜单打开全局导航抽屉，返回回到当前对象所属列表。不要用另一个菜单图标表达返回，也不要把返回绑定为展开全局导航。
- **每屏一个主要页面头部**：全局菜单入口融入页面自己的头部，不额外常驻“Workspace 栏＋页面栏＋详情栏”。Workspace 切换留在全局导航内；会话或电脑名称留在详情头部。
- **页面操作属于当前任务**：搜索、新建、更多操作只有在页面确实支持时才提供；不要为了填满顶部空间添加装饰性或重复入口。
- **抽屉是临时导航**：选择目标后收起；提供明确关闭按钮、点击遮罩和 Escape 关闭路径，键盘与触屏都可操作。跨手机／桌面断点时关闭临时抽屉，桌面折叠状态独立保留。
- **断点统一**：当前 Web 使用 `md`（768px）区分这两种布局。CSS 与交互判断必须一致，不能每个功能各定一套手机宽度。
- **实现复用，状态归属清楚**：全局抽屉由 [AppShell](../apps/web/src/components/app-shell.tsx) 管理，页面通过 [MobileNavigationButton](../apps/web/src/components/layout/mobile-navigation.tsx) 接入；普通标题栏复用 [PageHeader](../apps/web/src/components/layout/page-header.tsx)，详情头部提供自己的返回控件。列表选择、滚动和草稿由功能模块维护，不搬到全局导航组件里。规范要求保留用户状态，不限定必须靠常驻 DOM 实现。

### 2.2 手机页面是一张连续的内容表面

- 手机端不为隐藏的全局侧边栏保留空列。列表与详情占满可用宽度，移除仅为桌面并排面板服务的外侧留白、圆角和边框；内容内部确有分组意义的卡片不因此全部删除。
- 顶部、正文和底部输入／操作区使用协调的语义底色，必要时用细分隔线区分。不要把桌面侧栏底色直接搬成一条额外顶栏，或用多层不同底色掩盖重复的导航结构。
- 聊天等固定高度页面让内容区承担滚动，头部和输入区不能因多叠一条栏而超出可视区域。一般列表或表单不强制套用聊天页的固定底部输入区。

## 3. 说明按需出现，不默认铺满页面

新增说明文字前，先问：能否通过更准确的标签、分组、单位或控件让含义直接成立？已经由界面表达清楚的内容直接删除，不必换成一个问号。

| 信息类型                                   | 默认呈现                                                     |
| ------------------------------------------ | ------------------------------------------------------------ |
| 字段名、当前值、必要单位、主要操作         | 直接可见                                                     |
| 不知道就容易填错的格式或限制               | 字段附近的简短提示                                           |
| 术语定义、为什么需要这个选项、次要补充     | 标签旁帮助入口，按需展开                                     |
| 多段解释、示例、详细规则、含链接的内容     | 点击展开的帮助、原生 disclosure 或合适的面板，不塞进 Tooltip |
| 错误、权限限制、影响操作的风险、不可逆后果 | 在相关操作或字段附近直接可见，不藏进帮助                     |
| 日志、来源、方法和详细诊断                 | 摘要后按需查看；影响结论的限制仍随摘要可见                   |

例如，一个含义不熟悉的设置项可呈现为“设置名称 [?] + 当前值”，把背景解释放到帮助里，而不是在输入框下常驻一段说明。标签本身仍必须有意义，不能依赖打开帮助才能辨认选项。

帮助入口要求：

- 简短、非交互说明可复用现有 [Tooltip](../apps/web/src/components/ui/tooltip.tsx)。鼠标悬停与键盘聚焦均能获取说明；不能仅靠颜色或浏览器 `title`。
- 问号等图标使用现有图标库，触发器有可理解的可访问名称，例如“关于设置名称”。不要把每个标签都配上装饰性问号。
- 触屏用户必须有点击可用的获取方式；若现有 Tooltip 不满足，使用合适的点击展开交互，不假设手机支持 hover。
- Tooltip 不承载链接、按钮等需操作的内容。需要交互时使用支持相应焦点和关闭行为的展开面板或对话框。
- 帮助不抢输入焦点、不遮住当前操作，并验证键盘关闭、焦点可见和窄屏定位。

“渐进披露”不是把所有文字藏起来，而是让默认界面足以完成普通任务，解释与细节在需要时可达。

## 4. 用真实内容建立清晰层级

- 支持快速浏览和深入检查两种路径：标题、当前值、状态与动作能说明核心内容；详细记录可按需查看。
- 每份信息有一个主要位置。不要让摘要、说明卡片、提示横幅和结尾总结重复同一个意思。
- 使用具体名词和动作。空状态说清如何开始，错误说明发生了什么以及可用的恢复方式；不写“开启智能协作之旅”“无缝释放潜能”等填充文案。
- 不把设计过程写进产品文案，例如“我们将信息分为以下几个部分”。不新增没有依据的紧迫性、推荐、统计数字或成功声明。
- 保留数据的单位、范围、时间和不确定性。模拟数据须明确标识且不携带真实敏感信息，不用漂亮的虚构指标增加可信度。
- Agent 在线状态与活动独立表达，不把在线解释为正在工作，不把消息已被接受解释为运行完成。

## 5. 让组件承担重复决策

- 优先使用现有 Button、Dialog、Tooltip、Select 等原语。只有真实重复需求才沉淀共享模式，不为单个页面新建一套设计系统。
- 使用语义颜色。主按钮与品牌强调按既有规范区分；状态颜色同时有文字或其他非颜色线索。
- 同级元素使用一致的字号角色、间距和对齐。不要因为一段文字长就单独缩小它，也不要用极小浅灰字掩盖信息过多。
- 每个间距由一个布局容器负责，避免父子叠加 margin。留白服务于分组与重点，不留下无意义的大块空区。
- 表格和代码等内容获得足够空间，不因旁边一段说明被挤成窄栏。先重排，再考虑局部滚动；不能隐藏页面溢出来掩盖问题。
- 卡片、边框和底色须表达真实分组、选择或交互范围。避免卡片套卡片、普通元信息全部变成胶囊、每个标题都配图标与小标签。
- 动效仅用于反馈和状态连续性，尊重减少动态效果偏好，不给静态信息增加循环闪烁、逐段入场或模拟打字。
- 克制不是纯黑白模板，也不是禁止一切装饰。保留有依据的品牌表达，让主内容比辅助元素更突出。

### 加载与反馈样板

工作台覆盖聊天、Agent 列表和详情、Computer 列表和详情、设置首屏与个人资料保存。
创建和编辑 Agent、运行时凭据、Computer 运行时可见性使用就地错误与防重复提交。
参考 Linear 的稳定层级、Geist 的尺寸占位、Sonner 的连续反馈；保留 CoForge
品牌色和其他 Base UI 原语，Toast 使用 Sonner。以下时间与布局是样板的工程默认值，
不是 Figma 已发布的品牌标准，也不是对参考产品参数的复刻。

| 场景 | 呈现方式 |
| --- | --- |
| 首次进入消息页、Agent 列表 | 保留可展示的结构和静态标签，未知内容显示骨架；空状态只在读取完成且确实无数据时显示 |
| 切换私聊或频道 | 会话列表保持可用，目标内容区局部加载；不能在新目标下显示上一会话的消息或发送入口 |
| 已有列表刷新 | 保留真实内容、筛选值与输入元素，不重新显示骨架 |
| 会话加载失败 | 消息区域内说明失败并提供重试；保留会话列表和窄屏返回入口 |
| 个人资料保存 | 按钮显示保存中并阻止重复提交；成功在资料区简短确认，失败保留编辑内容并就地说明 |
| 短暂、非关键操作结果 | 共享 Toast；已有就地反馈时不再重复弹出 |

推广时保留已有的空列表、无搜索结果、Computer 未找到、频道加入、消息发送失败与重试界面；
不把这些确定状态换成骨架。安装指引、登录授权和立即发出的 Agent 控制命令不是页面数据加载，
保持各自的流程反馈。设置通知和时区的短暂失败沿用共享 Toast，不重复增加提示层。

- 样板路由使用 `pendingMs: 300`、`pendingMinMs: 0`：避免快速请求闪屏，
  不为了播完动画延迟真实内容。此策略不承诺在 JS 或认证信息尚未加载时渲染完整工作台。
- 骨架沿用最终布局的间距、列数与容器尺寸；只提示头像、文字、列表等主要轮廓，
  不伪造状态点、未读数或运行进度。使用中性 Token 与轻微同步明暗变化，减少动态效果时静止。
- 骨架装饰从可访问树隐藏，区域标记 `aria-busy`，一组内容只发出一次加载提示。
  加载文案仅供屏幕阅读器读取，不在骨架上重复显示 Loading；保留标题区和真实返回入口。
  不让不可用的占位控件进入键盘操作顺序。
- 头像和资料不是原子事务。头像成功、文字失败时明确说明部分成功，保留文字，
  重试不重复已完成的头像操作；未经服务端确认不能声称回滚或全部保存成功。
- Toast 在桌面位于右下角，手机（小于 768px）位于顶部居中，留出安全区；最多同时显示三条，同类型、同标题更新原条目。
  使用中性浮层、细边框、图标与简短文案，避免大面积红绿底色。正文错误色使用
  `destructive-text` 而非填充色。使用 Sonner 默认四秒自动消失、不显示关闭按钮，保留原生堆叠、展开与减少动画支持。
  `AppToastProvider` 统一 Toaster 配置，`useAppToast` 仅负责去重与安全错误编号，不自行实现通知队列。
- Toast 不自动抢焦点。配置 F6 进入通知区；交互期间的暂停计时由 Sonner 负责。
  Escape 折叠通知堆叠，不承诺恢复到触发前控件；通知采用 Sonner 的礼貌播报。
  必须处理的错误、断线状态、消息发送失败和字段校验不能只存在于短暂 Toast。
- 通用页面还应区分无数据、无搜索结果、无权限、失败与刷新，不用一个空状态覆盖它们。
  加载、消息已接受、Agent 在线与 Agent 活动是不同事实，不互相推断。

### 5.1 空状态复用组件，但不混淆业务状态

- 列表、会话等主要内容区确认没有数据时，复用 [Empty 组件](../apps/web/src/components/ui/empty.tsx)：`Empty` → `EmptyHeader` → `EmptyMedia`、`EmptyTitle`、`EmptyDescription`。使用与对象相关的小图标、可理解的标题和必要的简短提示，不在大片空白中只放几行裸文字，也不默认加入大插画、动效或多层卡片。
- 图标沿用现有图标库及语义颜色，不单独引入一套插画或配色；装饰性图标对辅助技术隐藏，标题与说明保留可读文本和正确语义。展示复用组件，是否为空及显示哪段本地化文案由功能模块决定。
- 区分“尚无数据”“尚未选择对象”“没有匹配结果”“正在加载”和“加载失败／无权限”。不能把请求失败、仍在加载或未选择对象显示成“No messages yet”；不要仅凭空数组忽略现有加载、错误与权限状态。
- 只有确实能推进当前任务且用户有权限时才增加操作按钮，例如新建或清除筛选。已有可用的聊天输入框时，不再增加一个重复的“开始聊天”按钮。
- 有数据后恢复正常列表或内容；空状态不能与非空内容同时占据同一内容区域。线程等局部空状态保持紧凑，不挤走根消息或输入区。

## 6. 渲染检查与反馈闭环

UI 变更必须查看实际渲染，不以源码检查代替视觉检查。按影响范围覆盖默认、加载、空、错误、禁用和展开帮助等状态，以及长中文、英文、代码、窄屏和明暗主题。纯交互改动检查 DOM、键盘与触屏行为；外观改动保留并检查代表性截图。

交付前先检查：

1. 第一眼能否看清主要任务、当前上下文与可用动作？
2. 是否有可以删除、改成准确标签、或移到按需帮助里的常驻说明？必要风险是否仍直接可见？
3. 同级内容是否对齐、正文是否清晰，是否有无意义的留白或重复容器？
4. 帮助是否能用鼠标、键盘和触屏获取，展开后是否遮挡操作？
5. 是否存在意外横向溢出、截断、低对比度或无法到达的操作？
6. 错误与空状态是否真实，文案是否保留业务含义？

涉及上述模式时，再执行对应的交互验收：

- 列表入口 → 选择对象 → 详情 → 返回列表，确认一次只显示正确的手机面板，列表上下文与草稿保留；分别打开列表 URL 和详情深链接，不只验证已经选中的页面。
- 打开全局菜单、选择目标、关闭抽屉；跨 `md` 断点检查抽屉关闭、桌面折叠状态保留以及手机没有空列。检查 767px／768px 两侧与代表性的手机、桌面宽度，不只截默认一屏。
- 检查每屏只有一个主要头部、标题和操作不重叠、输入区可达；空状态覆盖手机／桌面与明暗主题，并验证数据出现后消失，错误或加载状态不被误报为空。
- 在功能公开接口上保留相应回归测试；布局可见性和实际滚动需要浏览器验证，不能用不执行 CSS 断点的 DOM 测试替代。记录已执行的检查和限制，不把尚未建立的自动化检查宣称为 CI 保证。

这些规则约束后续新增和修改的同类页面，不表示历史页面已全部完成适配；不要求每次任务顺带批量改造无关页面。

改进规范从一个重复场景开始，不先建设大型评测平台：

- 先记录近期重复出现的设计修正，改写成可观察规则，而不是“更高级”“少点 AI 味”。缺少实际反馈时将新规则视作待验证假设，不声称已有评测证据。
- 固定一个任务的提示词、模拟输入、模型配置和视口，保存没有新指导的首次输出，再保存有新指导的首次输出，不择优重抽。
- 预先写下评价标准，打乱前后顺序做人工比较。起步可选聊天页；扩展时加入设置页和列表页，防止规则只适合一个布局。
- 记录指导版本、截图和具体反馈。单次对照只能发现明显问题；要评估稳定性，再做多次独立生成，并保留未参与规则调优的场景。
- 判断类修正写入本文；重复的视觉机制落到样式或组件；可检测的失败转成确定性检查。不要把单个模型的一次异常直接变成全局禁令。
- 修改后重跑受影响场景，阶段性跨场景复查。机械检查只能验证已编码的问题；层级、内容选择和整体设计质量仍需人工判断。

本节定义后续工作方式，不表示仓库已经具备自动视觉评测平台，也不要求每次小修都重新生成整套页面。
